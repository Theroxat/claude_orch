# Security model

orch is for **small teams who trust each other**. It is a shared to-do list with automation, not a multi-tenant platform. Read this before you adopt it.

- **Trusted teams only.** Anyone who can get an issue labeled for the pool can, in effect, write a prompt that runs on a teammate's machine. Do not use orch with strangers or with public repos where outsiders can file labeled issues.
- **What the sandbox does.** Each task runs in its own container, non-root, with only that task's clone mounted. No docker socket, no host home directory. Each task gets an isolated clone, not your working copy. Git metadata (the bare mirror and the clone's `.git` bookkeeping) is kept outside the task container, so a task cannot rewrite hooks or config that the agent's own git would later run.
- **The repo's compose file is validated.** When a task uses the repository's own `compose.yaml` for its dev environment, the agent checks it before starting anything and refuses `privileged`, host bind mounts, the Docker socket, host networking and `cap_add`. This validation is being completed on the agent side; until it ships, treat a repo's compose file as trusted code. It is not a defence against a hostile teammate.
- **What the sandbox does not do.** In auto mode the agent runs `claude -p --permission-mode bypassPermissions` inside the task container. That container has **network access** and receives **the member's Claude token**. A malicious or compromised issue can therefore make Claude exfiltrate that token, call external services, or push harmful code to the task branch. There is no egress filtering in v1. The token is the member's own and can be revoked from their Claude account.
- **The agent is root-equivalent on the member's host.** The agent container mounts `/var/run/docker.sock` to start task containers. Anyone controlling the agent controls that Docker daemon. Rootless Docker is a supported way to reduce this.
- **Claude credentials never leave the member's machine.** The token lives in the agent's local volume and in that member's task containers. The server stores no Claude credentials. The agent mounts `~/.claude` read-only, only to estimate usage.
- **Usage figures are estimates.** Anthropic does not publish exact subscription limits. Budgets, margins and reset times come from local logs plus a safety reserve and may be wrong. Treat them as hints.
- **Review PRs.** Auto-mode PRs are drafts. Enable branch protection and require human review before merging. The GitHub App's `Contents: write` can push to any branch.
- **Who can sign in.** Production requires admins (`ORCH_ADMIN_GITHUB_LOGINS`) and/or an allowlist of GitHub logins or organizations (see {ref}`access-control`). Admins approve everyone else on the Access page; a refused sign-in creates no session, only a request form protected by a short-lived HMAC-signed token, the Origin check and a rate limit. Invite links are stored hashed and expire. A task board is visible only to the project owner, active participants and GitHub collaborators; owner rights are re-checked against the GitHub ADMIN role (cached a few minutes), so a former admin loses them.
- **GitHub outages: last known decision for 15 minutes, then fail closed.** Organization membership is checked with the user's GitHub token. When that check fails (network error, 5xx, rate limit, or a 401 because the user revoked the orch App authorization in their GitHub settings), the user's last known allow/deny decision is reused only if it is younger than `ORCH_ACCESS_GRACE_SEC` (default 900 seconds). After that, or with no earlier decision, the user is refused: sessions, personal tokens, OAuth tokens and agents alike. A failed check is not retried for 30 seconds, so an outage does not turn every request into a GitHub call. A revoked App authorization never grants access: it is "unknown", gets the same grace, then is refused; so is a GitHub token that can no longer be refreshed. Admins, logins in `ORCH_ALLOWED_GITHUB_LOGINS` and logins approved on the Access page do not depend on GitHub and are unaffected. A refused member's agents are disconnected with the non-fatal close code 4403 (an upgrade gets HTTP 403) and receive no offers; they reconnect on their own once access is restored. Tasks already running keep their GitHub installation token until it expires (at most one hour).
- **Live task logs.** While a task runs in auto mode, the agent streams a compact form of Claude's output (messages, tool names and short arguments, the start of tool results, stderr) to the server, which shows it on the task card (see {ref}`live-logs`). The agent masks secrets before anything leaves the machine (see {ref}`redaction`), strips terminal escape codes, and the server masks the secret formats again. Masking only catches known values and formats: a secret it does not know can still appear. Logs are readable by exactly the people who can see the task board (project owner, active participants, GitHub collaborators, with the same rules for private repositories), are kept in server memory only (512 KB per run, 30 minutes after the run, never in the database or backups), and an open stream is re-authorized every 2 minutes, so removing someone stops their stream within that delay. Only the agent running an assignment can write to its log.
- **Server side.** Only Caddy is published. Postgres and the server are internal. GitHub user tokens are encrypted with `ORCH_ENCRYPTION_KEY`. Agent credentials and personal MCP tokens are stored hashed. Webhooks are verified with HMAC and deduplicated by delivery id and by body hash. Caddy sends HSTS and a strict Content-Security-Policy, and the server never logs query strings (they carry the OAuth code). Every state change is written to an append-only audit log.

- **Rate limiting.** Requests are limited per signed-in user (or per client IP), with much stricter limits on sign-in, OAuth and enrollment endpoints, the webhook (also capped at 1 MiB per body) and the MCP endpoint (per token). New agent connections are limited per IP and an agent that floods messages is disconnected. Limits are in memory (single instance) and configurable, see {ref}`rate-limits`. The client IP is read from `X-Forwarded-For` only when the request comes from the trusted proxy (`ORCH_TRUST_PROXY`), so a spoofed header does not change the key. This slows down abuse and brute force; it is not a substitute for a firewall or Cloudflare in front of a public server.

Report vulnerabilities privately through GitHub security advisories on the repository.

## Redaction

One shared module (`packages/shared/src/redact`) masks secrets as `[REDACTED]`. It is applied to the live task logs (agent and server), the run log file on the member's machine, failure messages and summaries sent in `task.finished` (and stored as the run's reason), the PR body and the commit message orch writes, notification titles and bodies (every channel), and the agent and server logs (errors included).

**Known values** (agent only: the server never sees them). Every secret the agent knows for a run: the member's Claude token, the run's GitHub tokens, the agent credential, and the values injected into the task and sidecar containers (devcontainer `containerEnv`, build args, compose `environment` and `env_file` values once resolved, the password part of URLs). An env value is masked when it has 8+ characters, is not a common word (`production`, `postgres`...), a number, a version or a path, and either its key looks secret (`*TOKEN*`, `*PASSW*`, `*KEY*`, `*SECRET*`, `*_DSN`...) or the value looks random (12+ characters, letters and digits, entropy of at least 3.5 bits per character). Each value is also matched JSON-escaped, URL-encoded, in hex (both cases), in base64 and base64url (at the 3 byte alignments, so it is found inside a larger encoded blob such as a Basic auth header), and when line breaks (and the indentation after them) split it.

**Formats** (agent and server): Anthropic `sk-ant-` keys, OpenAI project keys, GitHub (`gh[pousr]_`, `github_pat_`), GitLab `glpat-`, npm, orch agent credentials and personal tokens, AWS access key ids (`AKIA`, `ASIA`...), Google API keys, Slack tokens (`xox*`, `xapp-`) and webhook URLs, Discord webhook URLs, Stripe `sk_`/`rk_` live and test keys and `whsec_` secrets, JWTs, private key blocks (PEM, OpenSSH, PGP, also JSON-escaped as in a GCP service-account file; an unterminated block is masked to the end of its body), Azure `AccountKey=` / `SharedAccessKey=` and SAS `sig=`, `Authorization` and API-key headers, credentials in URLs, and generic assignments such as `FOO_SECRET=...`, `"api_key": "..."` or `password: ...` when the value looks random (8+ characters, entropy of at least 3.5 bits per character, or 3 with both letters and digits; numbers, placeholders like `${TOKEN}` and code like `options.token` are left alone). AWS secret keys and GCP `private_key_id` values are caught by the generic rule through their key names.

**Streams.** Live logs and the run log are masked piece by piece with a small tail of the previous piece: a known value split between two lines or batches is masked on both sides (5+ characters of its start at the end of a line are masked there), a token cut at the end of a line masks the next line's leading token characters, and a private key block stays masked until its END line.

**Not covered.** Values the agent does not know and that have no recognizable format (a password printed by a test, a secret fetched at run time), other encodings (gzip, double encoding, a secret split into pieces by code), values shorter than 8 characters or too common to mask, and line-wrapped _format_ tokens inside one piece (only known values are matched across line breaks). Commit SHAs, UUIDs and base64 data (images) are not masked: there is no generic high-entropy rule outside assignments. After an agent restart, a run's env values are known again only once the run is prepared again. Masking is a safety net, not a guarantee: treat live logs like the repository itself.

**Cost.** All rules run in linear time (tested with adversarial inputs, no catastrophic backtracking); a 32 KB batch with 30 known values takes about 0.05 to 0.1 ms per KB.

## Limitations

- Single server instance (in-process scheduler); no high availability. One host, scheduled dumps.
- No egress control, devcontainer/compose sanitizing or token-injecting proxy for task containers (see "Future hardening" in {doc}`PLAN`).
- Usage and budget are estimates; plans are declared by the member.
- Repos must build from a `Dockerfile` or a simple `.devcontainer.json`; complex devcontainer features are not honored.
- Manual-mode `screen` sessions end if the agent container restarts; the task container survives and `orch attach <n>` reopens a session.
- One concurrent task per machine by default.
- GitHub only. English UI only.
- The production images run TypeScript through `tsx` rather than a compiled build; the server image is still about 380 MB (Alpine, trimmed Prisma CLI).
